# Performance Ledger

## Claim boundary

上一版候选已取得单人代表性基地运行时数据，但性能门槛未通过。当前候选已替换热点身份校验，并基于同一份采样数据合并容器扫描回调。用户在同一代表性基地的主观复测结果为：持续掉帧已消失，任务接近瞬时完成，但执行期间仍有一次短暂、明显的掉帧。尚无当前候选的量化切片数据；联机与专服客户端也尚未测量。不能声称“无卡顿”或多人性能已验证。

已静态确认：

- 生产脚本没有 `FindAllOf`。
- 只枚举当前基地的 `MapObjectInstanceIdRepInfoArray.Items`。
- 物品元数据只按本次背包中的唯一物品 ID 查询。
- 路由使用 `containersByContainedItem` 与 `containersByAcceptedCategory`。
- 库存、基地对象、容器槽位、路由决策和提交前容量复核都有固定批量上限；
  单个物品也不会在一个切片内遍历任意数量的兼容容器。
- `RequestMoveToContainer_ToServer` 只有一个调用点，目标请求由 34 ms 串行链驱动。

## 2026-08-30 单人热点采集

环境：Palworld Steam build `24575825`，Workshop UE4SS `3.0.1`。

第一次聚合采集：

- 任务总时间 `12.093 s`，186 个调度切片，最长切片 `79 ms`。
- 当前基地 445 个复制对象，19 个支持的目标容器，共 545 个容器槽位。
- 基地对象阶段 `4.099 s`；容器阶段 `2.465 s`；只提交 1 个目标请求。

第二次细粒度采集：

- 任务总时间 `13.163 s`，187 个调度切片，最长切片 `87 ms`。
- 当前基地 446 个复制对象，19 个支持的目标容器，共 545 个容器槽位。
- 446 次 `FindModel`/`ConcreteModel` 路由累计约 `4 ms`；114 次目标判型低于计时分辨率；545 次槽位数组读取与物品 ID 解码合计约 `6 ms`。
- 基地对象阶段仍为 `4.670 s`，容器阶段仍为 `2.513 s`。两阶段未被细粒度调用计时解释的成本与每个切片开头执行一次完整 `identityMatches` 一致，约为每次 `40–42 ms`。
- 本轮 4 个合格背包槽位、共 5 件物品全部走 `filter` 路径；没有 `exact` 或 `incubator` 分配。因此原生 exact-only 快路不能解决该代表场景。

结论：主要回归不是基地对象或容器槽位枚举本身，而是每个小切片都重新解析 controller、player state、pawn、world、base 并多次调用 `GetFullName()`。第一阶段修复已将切片身份校验替换为这些对象的 `GetAddress()` 与基地 GUID 比较，并保持任一身份不可读或发生变化时立即中止。第二阶段把三个扫描批量提高到 64；用户主观复测显示明显改善但仍有持续掉帧。第三阶段据此把基地对象批量提高到 256，并让一个切片共享“最多 16 个容器、256 个槽位”的双重预算，消除每个小箱子独占两个回调的固定等待；提交前容量复核批量也提高到 256。主观复测显示持续掉帧已消失、总时间显著缩短，但仍需以相同场景采集量化数据。

第三阶段细分采样：

- 代表运行处理 444 个基地对象、19 个目标容器和 545 个容器槽位，共 15 个切片，最长切片 `77 ms`。
- `identityMatches` 调用 16 次，累计 `576 ms`，最长 `40 ms`。
- 其中 `UEHelpers.GetPlayerController()` 路径累计 `575 ms`；随后解析、验证、GUID、地址和比较合计约 `1 ms`。
- 已核对本机 Workshop UE4SS 的 `UEHelpers.GetPlayerController()` 实现：每次调用都会执行 `FindAllOf("PlayerController")`，这解释了约 `35–40 ms` 的固定切片成本。

当前修复将该 helper 限制在任务开始或缓存失效时使用。任务切片复用已验证的 Controller，但仍重新读取和验证完整对象链，并比较 Controller、PlayerState、Pawn、基地组件、Base、World 的原生地址及基地 GUID。运行效果待复测。

本轮候选继续收窄冷启动和提交前复核：缓存失效时先调用
`FindFirstOf("PlayerController")` 并验证本地 Controller，仅在失败时进入
UEHelpers 兼容回退；目标模型与 ConcreteModel 的二次身份校验由
`GetFullName()` 改为 `GetAddress()`；PalUtility、静态目标类型和同一
GameSetting 的物品分类表复用有效缓存。提交后的完成确认每 120 ms 只读取
本轮成功提交涉及的来源背包槽位，最多 3 秒，不增加常驻 Tick 或全局扫描。
游戏内开始提示会创建一个与 Pal Insight F7 同款的轻量 UMG 状态条；详细结果卡
使用独立的离屏分片构建，并按触发时冻结的“自动 / 仅文字 / 仅结果窗”策略选择。
结果窗关闭完全由鼠标、键盘及手柄事件驱动，不再轮询按钮状态；只在游戏切换
输入模式时安排一次带 generation 校验的所有权恢复，不注册常驻 Tick。通知成本
必须包含在本轮复测中，不能从性能结论排除。

## 2026-08-31 当前候选细分采集

同一代表性单人基地的一次有效收纳：

- 背包 54 个槽位、40 种合格物品；当前基地 444 个复制对象、19 个目标容器、
  545 个容器槽位。
- 任务总时间 `1.391 s`，31 个切片，提交 6 个目标请求；最长切片 `42 ms`，
  位于提交前复核阶段。
- 6 次目标复核合计 `245 ms`：槽位扫描 `1 ms`、容量/来源校验 `1 ms`、
  请求参数准备低于计时分辨率，而 6 次同步 Lua→UE RPC 调用合计 `242 ms`，
  单次最长 `42 ms`。
- 因此当前剩余帧时间尖峰不来自基地枚举、箱子扫描、路由、容量校验或 Lua
  参数构造；它位于 `RequestMoveToContainer_ToServer` 的同步调用边界，包含
  UE4SS 参数封送及原生函数执行，现有采集不能再区分这两者。
- 结果卡离屏分片构建总工作时间由上一候选的 `32 ms` 降至 `13 ms`，最长
  UI 切片由 `4 ms` 降至 `2 ms`；缓存稳定 UMG 类对象的优化保留。
- 右侧滚动条安全留白实机观察正常。Saved 配置迁移成功；采集结束后新旧两份
  Saved 配置均已恢复 `PerformanceCapture = false`、`Debug = false`。

结论：继续缩小扫描批次或缓存 Lua 侧对象不会改善当前最长切片。直接目标 RPC
的 ABI 每次只能指定一个 `ToContainerId`，所以保持当前精确目标语义时无法把
多个箱子合成一次调用。下一项有意义但尚未验证的实验，是游戏原生
`PalBaseCampUtility.RequestMoveInventoryItemToBaseCamp(..., bQuickStackMode)`；
它可能一次处理多个来源槽位，但目标选择、箱子筛选、工会箱排除、帕鲁蛋和完成
时序仍是未知事实。在这些语义通过单独批准的受控运行时实验前，不能替换生产
路径或与当前直接 RPC 混用。

### 当前架构完整性能审计与最终候选

| 路径 | 当前证据 | 最终候选决定 |
|---|---|---|
| 空闲快捷键集成 | 2026-09-01 调查发现旧实现每 500 ms 还会完整执行 `SettingsUI.prepare()`，且所有延迟回调使用 UE4SS 旧异步 Lua API；崩溃转储显示 UE4SS worker thread 上的空指针读取 | 所有延迟入口迁移到游戏线程队列；500 ms 空闲路径只处理共享标量，16 ms 快速路径仅在 F6 设置栈打开时存在；等待一次实机复测 |
| F5 本地身份与输入门 | Controller 已缓存；暖路径没有 `FindAllOf`；resolve 最长 `4 ms` | 保持完整 fail-closed 身份复核 |
| 背包扫描 | 54 个槽位分 4 片但合计仅 `1 ms` | 每片上限由 16 调到 64，代表场景合为一片 |
| 唯一物品元数据 | 40 种分 5 片但合计仅 `2 ms` | 每片上限由 8 调到 64，仍为有界处理 |
| 基地对象与容器槽位 | 444 个对象 `7 ms`、545 个槽位 `6 ms`，单片最长 `4 ms` | 保持现有 256 上限；扩大将增加帧尖峰，缩小只会延长等待，且都不能影响 42 ms 主瓶颈 |
| 路由规划 | 2 片合计低于计时分辨率 | 每片上限由 32 调到 64；同优先级内优先复用已计划目标，尝试减少目标 RPC 数 |
| 提交前复核 | 扫描与校验各约 `1 ms` | 保持；这是容量、筛选、排除项和身份安全边界 |
| 目标移动 | 6 次同步 RPC 合计 `242 ms`、最长 `42 ms` | 仍保持每帧最多一个；ABI 只能指定单一目标，最终候选只通过减少目标数改善，不能消除单次调用成本 |
| 完成确认 | 只轮询已提交来源槽，最长 `2 ms` | 保持 120 ms/3 秒边界 |
| 开始通知 | 首次创建 `15 ms` | 提前以一帧一个稳定对象的方式预热 UMG 类和语言 CDO；不创建或缓存世界 Widget |
| 结果卡 | 离屏分片构建工作 `13 ms`、最长 `2 ms` | 保持；继续拆分只会延迟结果而没有帧预算收益 |

最终候选只合并上表中三项有数据依据的修改：减少等价目标请求、合并低成本
调度切片、分帧预热稳定通知对象。最终实机只安排一轮；采集同时记录请求数、
同级目标复用次数、各阶段切片、RPC、通知预热、开始通知和结果卡耗时。

### 2026-09-01 UTC 空闲卡顿与 UE4SS 崩溃候选

本轮调查的基线是持续走动时约一秒一次的短暂停顿，以及随后生成的一份
UE4SS 崩溃转储。该次加载并非严格的 Quick Stack 单模组环境：
`PalInsight/enabled.txt` 绕过了 `mods.txt` 中的禁用项，因此不能把症状强度
全部归因于 Quick Stack。不过转储中的异常线程不是 GameThread，而旧实现的
五个运行时模块均通过 UE4SS 旧异步 Lua 延迟 API 执行 Lua，其中设置集成还会
从该回调进入 UObject、viewport、DPI 与窗口缓存检查。该线程模型与
`0xC0000005` 空指针读取及周期性卡顿一致，足以建立本轮候选。

候选一次完成以下收口：

- 物品任务、通知、结果 UI 和一次性模态输入回收改用
  `ExecuteInGameThreadWithDelay`；活动运行时不再调用旧 `ExecuteWithDelay`。
- 500 ms 共享心跳、按需 16 ms 宿主 watcher 和面板打开期间的 80 ms 控制
  pump 各自只注册一个 `LoopInGameThreadWithDelay` 持久 action，并在不再需要
  时取消；不再每个间隔重新创建 UE4SS delayed callback。
- 设置树只在启动时通过游戏线程队列预热一次；500 ms 空闲心跳不再调用
  `SettingsUI.prepare()`。
- F6 关闭时没有 80/16 ms 主动 watcher；500 ms 心跳观察到设置栈打开后才
  启动 16 ms 请求信号循环，并以 80 ms 间隔复核宿主状态。

当本地 Saved 配置临时启用 `PerformanceCapture` 时，前 40 次空闲心跳只在
内存中累计耗时，约 20 秒后输出唯一一条
`perf_settings_heartbeat|...` 汇总；F5 仍输出既有的 `perf_capture|...`。
验收只需持续走动约 20 秒并按一次 F5。两条记录均不包含玩家、物品名称或
容器标识；采集结束后恢复为 `false`。

### 2026-08-31 最终候选一次性采集

- 54 个背包槽位、28 种合格物品、443 个基地对象、19 个目标容器和 545 个
  容器槽位；任务总时间 `1.106 s`，23 个切片。
- 背包、元数据和规划均合并为 1 片，最长分别为 `2 ms`、`2 ms`、`0 ms`；
  相比旧候选的 4/5/2 片，去除了 8 个低工作量调度等待。
- 同级目标复用发生 21 次；本场景仍提交 6 个目标请求，因此这次采集不能声称
  已减少 RPC 数，只证明复用分支实际生效。
- 6 次同步 RPC 合计 `242 ms`、最长 `45 ms`，仍是唯一显著且不可分割的尖峰；
  扫描、校验和参数准备合计不超过 `1 ms`。
- 静态通知预热分 14 片完成，总工作 `8 ms`、最长 `3 ms`；开始提示由旧候选
  的 `15 ms` 降至 `1 ms`。
- 原生物品行提前加载尝试耗时 `17 ms` 但未取得类，导致结果卡使用回退行，
  最长 UI 切片从既有路径的 `4 ms` 回归到 `12 ms`。该实验已撤回：最终源码
  恢复此前已实测的按需原生物品行路径，不保留失败的启动加载或回退行为变化。

因此不再安排额外实机轮次：保留已量化有效的调度合批与静态通知预热；保留
不改变优先级、且不会增加目标请求数的同级目标复用；撤回唯一负收益实验，恢复
此前已有实机数据的结果行实现。采集结束后 Saved 配置已恢复
`PerformanceCapture = false`、`Debug = false`。

## A/B 场景

在同一次游戏会话中准备并记录：

- 普通背包槽位数与唯一物品 ID 数。
- 当前基地复制对象数、支持的目标容器数及总槽位数。
- 目标请求数。
- 参考模组与候选模组各自的总任务时间、最长切片和明显帧时间尖峰。

参考模组和候选模组不能同时启用。每轮恢复相同背包与箱子状态，至少重复三次；处于测量噪声内的差异不写成性能提升。

## 当前一次性采集

候选配置新增开发开关 `PerformanceCapture`，仓库与发布种子必须保持
`false`。仅在用户批准的本地候选中临时设为 `true`，每次 F5 任务结束输出
一条以 `perf_capture|` 开头的稳定字段日志。它用于回答：

- 最长游戏线程切片属于哪个阶段，以及耗时多少；
- 身份解析、背包、元数据、基地对象、容器槽位、计划、提交复核和完成确认
  各自的切片数、累计耗时与最长切片；
- 开始和结束通知分别耗时多少；
- 本轮背包槽位、合格物品、基地对象、目标容器、容器槽位与请求规模。

采集不记录玩家、物品名称或容器标识。测量完成后必须把本地 Saved 配置恢复
为 `PerformanceCapture = false`，并在发布前再次确认所有诊断开关均为 false。
